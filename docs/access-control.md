# アクセス制御とロール

このドキュメントでは、Beamtime Management Systemにおけるアクセスレベルとロール、各機能へのアクセス条件について説明します。

## アクセスレベル

システムには以下の6段階のアクセスレベルがあります：

| レベル | ロール名 | 説明 |
|--------|----------|------|
| 1 | SELF | 自分自身の情報のみアクセス可能 |
| 2 | PI | Principal Investigator（主任研究者） |
| 3 | PROJECT_MANAGER | プロジェクトマネージャー |
| 4 | ALLOCATOR | ビームタイム割当担当者 |
| 5 | APPROVER | 承認者 |
| 6 | APPLICATION_MANAGER | アプリケーション管理者 |

## 機能別アクセス権限

### User Directory（ユーザーディレクトリ）

ユーザー情報の閲覧と管理を行う機能です。

#### アクセス条件

- **閲覧（表示）**: レベル3以上（PROJECT_MANAGER以上）
  - レベル3未満のユーザーには、メニューに「Users」が表示されません
  - 直接URLにアクセスしても、アクセス拒否メッセージが表示されます

- **ユーザー登録（New User）**: レベル4以上（ALLOCATOR以上）
  - レベル3（PROJECT_MANAGER）は閲覧のみ可能で、新規ユーザー登録はできません
  - レベル4以上のユーザーには「New User」ボタンが表示されます

#### 表示される情報

アクセスレベルに応じて、以下の情報が表示されます：

**レベル3以上で表示:**
- Account Name（アカウント名）
- First Name（名）
- Middle Name（ミドルネーム）
- Last Name（姓）
- Email（メールアドレス）
- Role（ロール）
- 機関（Institution）
- 所属部門（Department）

**表示されない情報:**
- Password（パスワード） - すべてのユーザーから非表示

#### 操作

- **ユーザー編集**: レベル3以上で各ユーザーの編集アイコンをクリックして編集可能
- **検索・フィルター**: すべての閲覧可能なユーザーが利用可能
  - 名前・メールアドレスでの検索
  - ロールでのフィルター
  - 機関でのフィルター
  - 所属部門でのフィルター

### Institution Management（機関・所属管理）

機関と所属部門の管理を行う機能です。

#### アクセス条件

- **閲覧**: すべてのユーザー
- **追加・編集・削除**: レベル4以上（ALLOCATOR以上）

レベル4未満のユーザーには以下のボタンが表示されません：
- 機関追加ボタン
- 所属追加ボタン
- 編集・削除ボタン

### バックエンドAPI権限

バックエンドでも同様の権限チェックが実施されています：

#### ユーザー管理API
- `POST /users/` (ユーザー作成): レベル6（APPLICATION_MANAGER）のみ
- `GET /users/` (ユーザー一覧): 認証済みユーザー
- `GET /users/{id}` (ユーザー詳細): 認証済みユーザー
- `PUT /users/{id}` (ユーザー更新): 権限に応じてフィールドレベルで制御

#### 機関・所属管理API
- `POST /institutions/` (機関作成): レベル4（ALLOCATOR）以上
- `PUT /institutions/{id}` (機関更新): レベル4（ALLOCATOR）以上
- `DELETE /institutions/{id}` (機関削除): レベル4（ALLOCATOR）以上
- `POST /departments/` (所属作成): レベル4（ALLOCATOR）以上
- `PUT /departments/{id}` (所属更新): レベル4（ALLOCATOR）以上
- `DELETE /departments/{id}` (所属削除): レベル4（ALLOCATOR）以上

## セキュリティ

### 多層防御

システムは以下の多層防御アプローチを採用しています：

1. **フロントエンド制御**: UIレベルで不正な操作を防止
   - 権限のないユーザーにはボタンやメニューを表示しない
   - アクセス拒否メッセージの表示

2. **バックエンド制御**: APIレベルで権限チェック
   - すべてのエンドポイントで認証・認可を確認
   - 不正なリクエストには403 Forbiddenまたは401 Unauthorizedを返す

3. **データベース制約**: データ整合性の保証
   - ユニーク制約（email, account_name）
   - 外部キー制約
   - NOT NULL制約

### 認証

- JWT（JSON Web Token）をHTTP-only Cookieで管理
- セッション有効期限: 60分
- ログアウト時にセッション無効化

## ロールの選択ガイド

適切なロールを選択する際の参考：

| ロール | 用途 | 対象者 |
|--------|------|--------|
| PI | 研究プロジェクトの責任者 | 主任研究者 |
| PROJECT_MANAGER | ユーザー情報の閲覧が必要 | プロジェクト管理担当者 |
| ALLOCATOR | ユーザー・機関管理、ビームタイム割当 | 施設運用担当者 |
| APPROVER | ビームタイム申請の承認 | 施設管理者 |
| APPLICATION_MANAGER | システム全体の管理 | システム管理者 |

## 初期セットアップ

システムの初期セットアップでは、最初のAPPLICATION_MANAGERアカウントを作成します。このアカウントから、他のユーザーを登録し、適切なロールを割り当てることができます。
